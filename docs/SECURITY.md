# Защита административного доступа

Плейбуки подготовлены для Ubuntu/OpenSSH/systemd и прямого SSH-подключения с
управляющего компьютера. Они не включены автоматически в deploy: сначала нужно
проверить альтернативный доступ и изменить локальный inventory. Подключения через
нестандартный ProxyJump, агент-only ключи и другой SSH-маршрут требуют адаптации
проверки нового соединения. Отпечаток сервера должен уже находиться в known_hosts.

## 1. Аудит без изменений

```bash
ansible-playbook -i inventory/server.yml playbooks/security-audit.yml
```

Показывает слушающие TCP/UDP порты, реальные Docker-публикации, SSH и UFW.
Текущая проверка Docker предназначена для публичного окружения: допускает только
публикации сервиса nginx на TCP 80/443; выявляет host networking. Это проверка
текущего состояния, не фильтр будущих публикаций и не внешний скан сети.
Наличие `5432/tcp` или `80/tcp` в EXPOSE контейнера не равно публикации на хосте.

## 2. Отдельный администратор

```bash
ansible-playbook -i inventory/server.yml playbooks/security-admin.yml
```

Создаёт пользователя deploy, .ssh/authorized_keys и проверенный sudoers-файл.
Использует публичную часть ключа `{{ ansible_ssh_private_key_file }}.pub` на
управляющем компьютере. Приватный ключ никуда не копируется. Можно переопределить
security_admin_user и security_admin_public_key_file.

Для автоматизации deploy получает `NOPASSWD: ALL` через sudo. Такой ключ даёт
административные полномочия: пользователь не добавляется в группу Docker,
но sudo остаётся полноценным способом получить root. Это не модель least privilege.
Парольный вход пользователя заблокирован.

Последняя задача открывает отдельное SSH-соединение с отключённым multiplexing,
без парольного fallback, с проверкой host key; проверяет `sudo -n id -u == 0`.
Root и парольный SSH-доступ на этом этапе ещё не меняются.

После успеха поменяйте `ansible_user` в личном inventory с root на deploy.
Проверьте вход в отдельном терминале, не закрывая существующую сессию:

```bash
ssh -i ~/.ssh/nextcloud_server -o IdentitiesOnly=yes deploy@YOUR_SERVER_IP
sudo -n id -u
```

## 3. Отключение root и паролей

Требуется рабочая консоль/serial console провайдера как резервный путь доступа.
Не закрывайте текущую административную сессию до окончания проверки.

```bash
ansible-playbook -i inventory/server.yml playbooks/security-ssh.yml
```

Плейбук требует `ansible_user=deploy`, проверяет новый вход и sudo ДО изменения.
Глобальный управляемый блок в начале sshd_config имеет приоритет перед обычными
Include/cloud-init-директивами. Проверяются `sshd -t`, итоговые параметры для deploy
и root, выполняется reload службы и повторная новая ключевая сессия.

При ошибке выполняется попытка восстановления предыдущего конфигурационного
файла и reload через существующую Ansible-сессию. Это не заменяет консоль провайдера:
при независимой потере сети автоматический откат тоже может быть недоступен.
Проверки Match относятся к указанным тестовым контекстам; после пользовательских
адресных Match-правил нужна дополнительная проверка с реальными источниками.

## 4. Firewall и ограничения IP

Плейбук security-firewall.yml включает UFW: разрешены SSH и TCP 80/443,
остальные входящие запрещены. Существующие разрешающие правила не удаляются.
По согласованию SSH доступен с любых IP, только по ключу; allowlist не задан.

Скрипт files/security/docker-ingress.sh подключает NEXTCLOUD-INGRESS через
DOCKER-USER для IPv4/IPv6: вход через ens3, существующие соединения и исходные
TCP-порты 80/443 пропускаются к следующим правилам Docker; остальное DROP.
Ограничение проверяет порт, не имя контейнера. Публикации nginx проверяются аудитом.
Требуется iptables backend и DOCKER-USER обоих семейств. Для другого сервера
замените закреплённый ens3 в service-файле.

Служба связана с Docker через PartOf/WantedBy. После перезапуска Docker и полной
перезагрузки поведение пока не проверено. После ручной перезагрузки UFW проверьте
цепочки; при необходимости перезапустите nextcloud-docker-firewall.service.
Повторный запуск активной oneshot-службы сам по себе не исправляет дрейф правил.
Проверки новых SSH-сессий выполняются до/после настройки; автоматического отката
firewall нет. Сохраните существующую сессию и консоль провайдера.

На текущем сервере подтверждены UFW, цепочки IPv4/IPv6 и работа SSH/сайтов.
Внешний отрицательный тест и перезагрузка ещё не проверены.

UFW защищает вход на сам хост, но Docker-публикации могут обходить его INPUT-правила.
Не отключайте Docker iptables/ip6tables как замену фильтрации: это может нарушить
сеть контейнеров. Нужно учитывать backend Docker, входящий интерфейс и forwarding
либо использовать согласованные Security Groups провайдера.

Обычный SSH остаётся на порту 22: его смена сама по себе не заменяет ключи,
запрет root/паролей и ограничения источников.

## 5. Fail2ban для SSH

```bash
ansible-playbook -i inventory/server.yml playbooks/security-fail2ban.yml
```

Устанавливает Fail2ban, python3-systemd и iptables. Шаблон
templates/fail2ban-sshd.local.j2 доставляется в jail.d/99-nextcloud-sshd.local.
Проверяет полную конфигурацию, перезапускает службу при изменении и проверяет sshd.
Другие ранее включённые jails сохраняются. Применение на сервере пока не подтверждено.

backend=systemd читает журнал; maxretry=5, findtime=10m, bantime=10m:
5 распознанных ошибок за 10 минут блокируют IP на 10 минут.
iptables-multiport ограничивает SSH-порт, не сайты или DOCKER-USER.
Loopback исключён; домашний/VPN IP автоматически не исключается.
Это дополнение к ключам, не защита от кражи действующего ключа.

```bash
sudo fail2ban-client status sshd
sudo fail2ban-client get sshd maxretry
sudo fail2ban-client get sshd findtime
sudo fail2ban-client get sshd bantime
sudo journalctl -u fail2ban --since '10 minutes ago' --no-pager
```

Разблокировка из оставленной сессии или консоли провайдера:

```bash
sudo fail2ban-client set sshd unbanip YOUR_IP
```

Не проверяйте бан неудачными входами с единственного рабочего адреса.
